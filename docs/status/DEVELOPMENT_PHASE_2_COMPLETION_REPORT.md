## API contract

| Method/path | Phase 2 behavior |
| --- | --- |
| `POST /auth/register` | Business User identity; Argon2id hash; verification token and encrypted intent |
| `POST /auth/email/resend`, `POST /auth/email/verify` | Enumeration-safe resend; one-use, expiring verification |
| `POST /auth/password/forgot`, `POST /auth/password/reset` | Enumeration-safe recovery; one-use, 15-minute token; reset revokes sessions |
| `POST /auth/login` | Password check; staff/opted-in MFA challenge or session cookie |
| `POST /auth/mfa/setup`, `POST /auth/mfa/verify` | TOTP enrollment and challenge completion before staff session issuance |
| `GET /auth/session`, `POST /auth/logout` | Current identity, role, business state and destination; CSRF-protected session revocation |
| `GET /auth/access/admin`, `GET /auth/access/business/:id` | Direct API role and approved-owner policy probes; 401/403 on denial |
| `GET /health`, `GET /metrics` | Preserved Phase 1 dependency health and Prometheus output |

All request bodies are strictly validated at the edge. Account identifiers are normalized to lowercase email. The login response distinguishes a valid but unverified or suspended account only after a correct password; invalid username/password receives the same generic 401. No role or approval is inferred from a hidden UI control.

## Security details

Passwords use Argon2id and are never stored in plaintext. Session, CSRF, email-verification, password-reset and MFA-challenge tokens are generated from cryptographic randomness; only SHA-256 hashes of token values are stored in their primary tables. Notification-intent token payloads and TOTP secrets use AES-256-GCM at rest under `AUTH_ENCRYPTION_KEY`. Token and notification-intent creation is transactional. The key must be a unique 32-byte hex value per environment; production requires an HTTPS `WEB_ORIGIN` and externally injected secrets.

Sessions are server managed, seven-day maximum, expiring and revocable. Logout revokes its session; reset revokes all the user's sessions; suspension can revoke sessions through the Users service, and every session read checks current account state. Session cookies are HttpOnly, SameSite=Lax and Secure in production. A separate CSRF cookie is checked against the server session on logout; browser state-changing requests also check Origin. Staff receive no session until TOTP succeeds. Verification/reset links carry the one-time token in a URL fragment, keeping it out of HTTP paths and Next access logs; the fragment is cleared from browser history on use. Authentication does not grant approved-business marketplace rights.

Security/audit records capture registration, verification, login outcome, password recovery/reset, MFA completion/denial and role denial with actor, action, resource, outcome and time. No public audit mutation endpoint exists. No password, session token, recovery token, MFA secret or OTP is logged by the API. Outbound email/SMS providers are not called inside authentication transactions.
