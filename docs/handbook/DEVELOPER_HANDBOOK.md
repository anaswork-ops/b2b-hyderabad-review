# B2B Hyderabad V2 — Developer Handbook

Status: **Step VI manually approved and frozen on 2026-09-18.** This is an operating guide to the approved Step V structure, not permission to implement Development Phase 1. Paths below describe **planned destinations** unless stated as present. Exact class, function, endpoint, and configuration filenames remain phase implementation decisions.

## 1. Start here: authority, product, and gates

B2B Hyderabad V2 is a B2B travel marketplace and business collaboration platform. The Hajj & Umrah first MVP supports business onboarding, approved supplier profiles and offerings, availability-aware discovery, comparison, custom requests, messaging, notifications, and governance. Tourism and Visa Services are distinct top-level verticals in the architecture, but the approved phase contracts determine their MVP depth. The platform is neither Nusuk nor a Saudi government authorization system; platform approval is not external accreditation.

Read, in order: `AGENTS.md`; `docs/source-of-truth/INDEX.md`; the frozen Requirements Specification (PDF authoritative over its Markdown transcription); frozen Technology Baseline; approved Master Codex Implementation Plan (PDF authoritative); `docs/architecture/PROJECT_STRUCTURE.md`; this handbook once approved. The Step V report records validation, not new requirements. The requirements control behavior, the technology baseline controls technology lines, the plan controls phase scope, and the Step V structure controls physical ownership. This handbook explains how to operate within them; it cannot amend them.

The eight development phases are: 1 foundation and application skeleton; 2 identity/security; 3 application and approval; 4 profiles and inventory; 5 marketplace; 6 enquiries/messaging; 7 administration; 8 landing, hardening, release qualification. Only a phase explicitly authorized by the user may run. Each phase reads its contract, implements only that scope, validates, reports, then **stops for manual user acceptance**. Step VI itself ends at its own manual gate. A frozen requirement change requires explicit agreement and a recorded revision; an engineering choice within a phase does not.

## 3. Environment configuration and secrets

Environment files exist because the same build needs different non-code settings in local development, staging, and production: database/queue endpoints, object-storage endpoints, public origins, feature-independent operational settings, and credentials. Local `.env`/`.env.local` files are ignored and machine-specific. `.env.example` lists names, descriptions, and harmless placeholders only; it is a setup contract, not a credential store. Staging and production values come from a deployment secret-management system or injected environment, with separate accounts/data and access controls. Production data must not be used in development or testing.

API keys, database passwords, SMTP credentials, SMS/provider credentials, S3 credentials, session signing or encryption keys, MFA encryption secrets, and similar values belong in server-side environment variables or a production secret manager. They do **not** belong in source files, frontend bundles, docs, logs, Git, committed Compose files, test snapshots, or error responses. `NEXT_PUBLIC_` style values are intentionally exposed to browsers and therefore may contain only public configuration, such as a public origin; never put a credential behind that prefix. API and worker configuration loaders validate required names, types, allowed environments, and safe startup invariants before serving or consuming jobs. Exact variable names and validation code are Phase 1+ choices.

Give each service the least privileged credential it needs; avoid sharing a production superuser DB password across API, worker, and backup jobs. Rotate leaked/expired keys through the provider/secret manager, update deployments, verify service health, then revoke old keys. If a secret is committed, removal from the latest file is insufficient: treat it as exposed, rotate it, and follow repository incident handling. Log correlation IDs and sanitized failure categories, never raw authorization headers, tokens, message contents, private documents, or config dumps.

## 4. Control flow and entry points

These are conceptual chains. Phase implementation chooses actual functions, endpoint names, and exact files.

```text
Browser request
  → Next.js route/layout (src/app route group)
  → feature view/model and typed src/lib/api adapter
  → NestJS controller + transport validation + authentication guard/policy
  → owning module application service (state/ownership/business rules)
  → owning repository via platform Prisma adapter
  → PostgreSQL
```

On protected operations the API guard establishes session and role; the owning policy/service checks approved-business state, resource ownership, and action permission. Route redirects and hidden controls only improve UX. Controllers translate HTTP and invoke services; they do not query Prisma. Services coordinate transactions and domain transitions; repositories contain owned persistence queries. A cross-domain call goes through an exported application service or narrow port, not another module's repository or table. Marketplace/Admin read composition uses explicit query services/projections.

```text
API business transaction
  → commit core state + durable notification intent/outbox together
  → post-commit dispatcher enqueues BullMQ job; failed enqueue remains retryable
  → worker job processor checks idempotency and delivery state
  → provider adapter sends email/SMS/etc.
  → record result, bounded retry/backoff, terminal failure visibility + metrics
```

Provider outage cannot roll back a committed application decision, message, profile edit, or package action. Queue/cache Redis is supporting infrastructure, not the system of record. A true failure of a required core DB write is different: the transaction fails and must not claim success. Exact outbox polling cadence, job names, attempt limits, and dead-letter mechanism are phase decisions to document and test when implemented.

## 5. Web ownership and UX boundaries

`src/app` owns routing, layouts, loading/error states, and entry-level data composition. `(public)` serves guests, landing, business discovery and vertical views; `(auth)` serves identity UX; `(applicant)` serves an applicant's own application; `(business)` serves approved-business work; `(admin)/admin` is one isolated route area inside the same web deployment. Route groups are organizational and do not create API permissions.

`src/features/<capability>` holds feature views, form composition, display models and local adapters. `src/lib/api` centralizes typed transport, error mapping, and server/browser-safe request behavior; it is not a second domain service. `src/lib/session` provides session-aware navigation and UX, never authoritative access checks. Use Next.js Server Components for server-side read/data composition where suitable and Client Components for actual browser interactivity; keep server-only values on the server. React components do not decide publishability, approval, search matching, price validity, or record access. The API enforces these rules even when a request bypasses the web app.

Keep market and search context visible and recoverable in URL or explicit navigation state. Public and approved-business contact views use distinct API projections. Hajj and Umrah share infrastructure but retain subtype-specific fields/rules. The marketplace requests indexed, paginated server results; a browser must not download all records for filtering. The final 8D landing experience, blue-sky visual identity, mobile performance and reduced-motion behavior belong to Phase 8, though the route shell exists earlier.

## 7. Database, schema, and migration practice

`database/prisma/schema.prisma` and `migrations/` are the one schema and migration chain for the one PostgreSQL database. Modules own their model sections by convention and review migrations affecting their records. The API's platform adapter constructs Prisma; a module repository uses that adapter to access only its owned data. Controllers never call Prisma. An application service can coordinate a single critical transaction across public module interfaces when the workflow requires atomicity; make the transaction boundary explicit and avoid holding transactions open across network/provider calls. Cross-module read models are explicit projections or exported query services.

Schema changes require a reviewed migration, referential integrity, data migration/backfill plan where needed, and rollback/recovery consideration. Never reset production to fix a migration. Seeds are opt-in synthetic dev/test setup; fixtures are deterministic factories. Index design and query-plan checks belong to modules proposing market, geography, date, availability, or pagination queries. PostgreSQL remains the transactional authority; Redis cache and queue must be rebuildable. Backups and restore procedures live under `docs/operations/` and deployment utilities under `database/scripts/`/`infrastructure/deploy/` in Phase 8. Periodic restore tests and rollback capability are release requirements.

## 8. Shared packages: reuse without leakage

`contracts` defines external HTTP shapes and stable event/job payloads. A versioned breaking change should be deliberate and tested against all consumers. `validation` defines matching Zod transport schemas for browser form checks and API boundary parsing; derive types from one canonical definition or generate from the contract to avoid hand-maintained duplicates. The API still validates business rules: state transitions, authorization, ownership, file policy, pricing/currency invariants and DB constraints cannot be settled by a Zod shape alone.

`types` holds only domain-neutral primitives that do not sensibly belong in contracts. `ui` holds accessible, unopinionated web primitives and design tokens; a business application wizard or marketplace filter workflow belongs in a web feature. `config` holds tool presets specific to execution targets; runtime secrets and a universal environment parser do not belong there. `utilities` accepts small pure helpers only after a documented second consumer; a one-use date helper stays local. Shared packages never import app code, Prisma, NestJS modules, Next.js routes, or environment secrets. Avoid barrel cycles and additions made solely to create apparent reuse. Consumer tests accompany contract or validation changes.

## 9. Worker, queues and isolation

The API persists notification intent with the core state; a dispatcher hands it to BullMQ after commit and reconciles enqueue failures. `apps/worker/src/jobs/` owns processors and operational retry behavior; `src/providers/` owns outbound integrations. Stable payloads include identifiers needed for idempotency and correlation, not credentials or unnecessary personal data. Processors must tolerate duplicate delivery, use bounded attempts/backoff, record terminal failures through a dead-letter or equivalent visible failure state, and expose queue age/failure metrics. Separate job priorities/queues may be justified by measured need; exact design is an authorized phase decision. Provider failure affects notification delivery, not the successful core business action. A message persistence failure, by contrast, is a core failure for that message operation.

## 10. Infrastructure and operating environments

`infrastructure/docker/` builds application images. `compose/` defines local PostgreSQL, Redis and S3-compatible dependencies and later staged variants. `proxy/` is optional if deployment needs ingress/reverse proxy. `observability/otel/` receives app traces/metrics; `prometheus/` defines scraping/alerts; `grafana/` provisions dashboards. `deploy/` holds staging/prod templates, health/readiness wiring, rollout and rollback. These are Dockerfile, YAML, JSON, or provider-specific configuration as selected in the relevant phase. No committed infrastructure file embeds a credential. Local Compose is for developer dependencies; staging validates complete workflows; production has separate data/config and a 99.9% monthly availability objective excluding planned maintenance. Deployment topology and exact provider choices remain phase decisions, not handbook commitments.

## 13. How to trace a feature

Start at the browser URL: find its `src/app` route group, then the feature component/view model. Follow its `src/lib/api` call to the contract/validation schema and NestJS controller. From controller follow guard/policy, application service, any public cross-module port, repository, and Prisma model/migration. Search for notification intent/job payload and worker processor if the feature communicates asynchronously. Finish at unit, integration, security, E2E and relevant load tests. Use symbol search and imports once code exists; this handbook does not promise exact names.

Reverse trace from a Prisma model by finding its owning API module repository and migration, then service/controller/contract/web callers. From an endpoint, find controller route, policy, service, transport contract, web adapter and tests. From a job, find producer/outbox, contract, worker processor, provider adapter, delivery state, metrics and retry tests. If no clear owner appears, stop and establish one before adding a generic shared helper.

## 14. Coding and architecture conventions

Use capability-oriented names and explicit domain language (`Business` vs `User`; `Source Market` vs `Business Location`; `Package` vs `Offer`). Let framework-required entry files follow framework conventions; choose remaining filenames in the implementing phase. Keep imports directed from app to shared packages and from domain to platform interfaces, never shared to app or sideways into another repository. Avoid cycles and giant barrel exports. Prefer narrow explicit services over redundant wrapper layers; optimize only with measured query/load evidence while keeping business logic reviewable.

Validate transport at the edge and business invariants in the owning service. Return stable typed errors without account enumeration, secret leakage or raw stack traces. Paginate server queries with deterministic ordering and bounded page size. Authorize every protected backend action against role, approval, ownership and permission; test direct API attempts. Audit privileged/security transitions with actor, action, resource, time and outcome. Use structured sanitized logs and correlation IDs. Keep critical DB steps in one transaction where required; never await a provider within it. Queue non-core delivery with durable intent and idempotency. Validate upload type/size and private access at API boundary. Do not introduce unfrozen staff management, microservices, Elasticsearch, Kubernetes, separate Admin deployment, or a generic `CommonModule`.

## 15. Change control, troubleshooting and phase reports

Classify a proposed change before editing. A **bug fix** restores frozen behavior and stays in the authorized phase; show the failed expected behavior and regression test. An **implementation decision** selects a concrete design within a frozen requirement and phase; record rationale and affected contracts without changing scope. A **requirement change** alters promised behavior, role, field, phase contract, technology line or structural authority; stop, propose a recorded revision and obtain user approval before incorporating it. Do not silently use this handbook to reinterpret source documents. Update the owning docs, index and handbook only after approved authority changes; preserve PDF source provenance.

When something fails, trace the boundary: route/adapter contract, controller validation and auth, owning service policy/transaction, repository/query plan, then outbox/queue/worker/provider. Check sanitized logs, traces, health and queue failure state. For environment failures, compare validated names with `.env.example`, verify each service uses its own non-production resources, and inspect local Compose health. For migration failures, use a disposable DB to reproduce and plan recovery; never reset production. For a provider outage, confirm the core action committed and delivery failure is visible/retryable.

Each authorized development phase ends with a completion report listing scope, files/modules, migrations, endpoints, UI, security controls, FR coverage, unit/integration/E2E/security results, lint/typecheck/tests/build, known limitations, deferred items, requirement deviations, manual test instructions and a STOP statement. Report failures honestly. The user then chooses APPROVED, CORRECTIONS REQUIRED or REQUIREMENT CHANGE REQUIRED. Approval of this Step VI handbook alone does **not** authorize Phase 1 unless the user explicitly says so.
